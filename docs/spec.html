0 The rules

  • Plan limits come only from the documented Claude Code status line feed. Tokens come only from the local transcripts. Mac figures come only from public macOS calls.
  • No Keychain item, credential, token or undocumented endpoint is read, ever, not even behind an opt in. Anthropic's legal page bars developers from collecting, storing or intermediating Claude.ai credentials or session tokens, verbatim, and reserves enforcement without notice.
  • No network call of any kind. No analytics, crash reports, update check or price fetch.
  • The product name does not contain "Claude", "Claude Code" or "Anthropic": the legal page bars their use "as part of your own product, feature, or company name". It allows saying in plain text that something runs Claude Code, so the UI says "Claude Code" as a fact.
  • Anthropic's terms say nothing either way about a local tool reading the transcripts or the status line feed; the status line documentation describes the feed as input for "any shell script you configure". That is silence, not permission, and the README says so.
  • The app reads only the fields and files named in this spec and drops the rest of every line: the feed fields of section 3, the transcript fields of section 5, the keys of Claude Code's session files named in section 5 and the two keys of settings.json (section 3). What it must never read is listed in section 5 and on the privacy page.

1 Architecture

  • Swift Package Manager only. No Xcode project. A package with swift-tools-version 6.0, platform macOS 14, seven library targets, one executable target tokenpanda linking AppKit, IOKit, ServiceManagement and UserNotifications, and one test target tokenpandaTests. Proven on the build Mac (Command Line Tools only, Swift 6.4, SDK 27.0): a status item plus popover package builds in 32 s with swift build -c release; SwiftPM signs the product ad hoc by itself. xcodebuild is not needed and not available there.
  • Minimum macOS 14, Apple silicon only. The widest floor among the AI usage meters; the package declares it. The release build is arm64 only: scripts/build-app.sh builds for the host. From 0.1.14 the cask declares depends_on arch: :arm64 and the README says "Apple silicon (M1 or later)", so an Intel Mac is not offered a build it cannot run. A universal binary is a release option, untested until someone tests it.
  • AppKit status item. NSStatusBar.system.statusItem(withLength: .variableLength); the button's image is a template image that ItemImage draws with the panda and the digits, set again only when the item's state changes; no redraw timer. SwiftUI's MenuBarExtra is not used: no custom drawing in the item, no fade on dismiss, no persisted selection.
  • NSPopover anchored to the item, 380 points wide, transient. Its root is a plain NSViewController whose view is an NSVisualEffectView for the glass (HUD material and a dark tint, or the popover material and a light tint, following the Mac's appearance) with one AppKit view, LineView, inside a clear NSScrollView. LineView draws the lines the Text module produces, 16 points each. No SwiftUI. The popover is one monospaced layout of lines, not controls stacked in a grid.
  • Panel height (from 0.1.14, PanelSize): as tall as its lines, at most the visible height of the screen the item is on less 60 points (the arrow, the gap under the menu bar and a margin at the bottom), never under 200 points. Beyond that the lines scroll, always with the overlay scroller, which takes no width and hides when idle, and with no rubber band at the ends. Every open of the popover and every tab click starts at the top. A control the keyboard focuses is scrolled into view with one line of room around it, and a tooltip that has no room above its line inside the visible part opens below it. VoiceOver reads every line of a capped panel. From 0.1.15 every line takes the accessibility focus, and when VoiceOver sets it there the panel scrolls that line into view with one line of room, as it does for the keyboard focus (section 20.5). 0.1.14 had no such handler on any macOS version, 26 and 27 included, so VoiceOver's outline could stand outside the visible part. The size is set when the popover opens and again whenever its lines change. Before 0.1.14 a long Settings tab or many sessions ran off a small or scaled screen.
  • Activation policy accessory (NSApp.setActivationPolicy(.accessory)) and LSUIElement true in Info.plist: no Dock icon, no app menu.
  • Not sandboxed. The transcript reader needs ~/.claude, the process list needs libproc, and the hook lives in Application Support. There is no entitlements file; the bundle's Resources hold AppIcon.icns and PrivacyInfo.xcprivacy. The Mac App Store is out of scope: it asks for a sandboxed app that reads and writes only its own container, and this app reads ~/.claude, writes settings.json and writes scripts: the status line script Claude Code runs, and the Reopen scripts Terminal, iTerm or Ghostty run.
  • No dependencies outside the SDK.
  • Swift 6 language mode with strict concurrency: the feed reader, the transcript store and the Mac sampler are actors, the UI state lives in one main actor controller.

3 The status line hook

The only source of plan percentages, verified on a Mac on 2026-10-13 against the documentation and a live capture.

How Claude Code runs it

  • Configured under the statusLine key of ~/.claude/settings.json: type is "command", command is a script path or an inline shell command, and the optional refreshInterval re-runs the command every N seconds (minimum 1) in addition to the events.
  • The script runs once when a session starts or resumes, then after each assistant message, after /compact, on permission mode and vim mode changes, when the command setting changes, when a timer elapses, and when a rate limit window in the last data reaches its resets_at. Updates are debounced at 300 ms; an in-flight script is cancelled when a new update triggers.
  • The first call of a session never carries rate_limits; every later call does (38 of 38 in the capture). With refreshInterval the timer fires while the session sits idle too. Between sessions the feed stops.
  • The feed reflects the account, not the one session: with two sessions open, both report the same account windows and the values move together.
  • Per session override for testing: claude --settings '{"statusLine":{"type":"command","command":"/path/hook.sh"}}' changes nothing on disk.

Even then, it appears only after the first API response in the session." And: "Each window (five_hour, seven_day, spend_limit) may be independently absent, and Claude Code drops a window once its resets_at time passes." There is no per model field and no plan tier field; the popover carries no tier badge.

The hook script

One job: copy stdin to a snapshot file, atomically, then hand the same input to the status line command the user had before, if any. It parses nothing, so it needs no jq, no python, nothing but sh.

#!/bin/sh
# The status line hook. Copies the feed Claude Code hands it to one file per session, atomically,
# then hands the same input to the status line command that was configured before, if any.
# It parses nothing and needs nothing but sh. The app fills in DIR and PREV at install time.
DIR='__DIR__'                 # filled in at install: the sessions folder in Application Support
PREV='__PREV__'               # filled in at install: the previous statusLine command, or empty
input=$(cat)
sid=$(printf '%s' "$input" | sed -n 's/.*"session_id":"\([0-9a-fA-F-]*\)".*/\1/p' | head -n 1)
mkdir -p "$DIR"
if [ -n "$sid" ]; then
  printf '%s' "$input" > "$DIR/$sid.json.tmp" && mv -f "$DIR/$sid.json.tmp" "$DIR/$sid.json"
else
  printf '%s' "$input" > "$DIR/latest.json.tmp" && mv -f "$DIR/latest.json.tmp" "$DIR/latest.json"
fi
# files of sessions that stopped writing over a minute ago, the same rule the app uses, so nothing piles up
# in the folder even when the app is gone
find "$DIR" -maxdepth 1 -type f \( -name '*.json' -o -name '*.json.tmp' \) -mmin +1 -delete 2>/dev/null
if [ -n "$PREV" ]; then printf '%s' "$input" | sh -c "$PREV"; fi
exit 0
  • refreshInterval is set to 5 when the user's entry has none of its own or a longer one (a session is open only while it writes within 10 s), and a shorter one stays, so the open sessions list and the reset rollover stay current while a session idles; the capture ran at 2 s with no visible cost. The script prints nothing of its own, so a user without a status line sees nothing new, and a user with one sees it unchanged.
  • DIR and PREV are both single quoted for sh, a single quote in them written as '\'', so no character in the data folder path or the chained command expands.
  • The snapshot is the whole feed JSON as received. The app reads only the fields in the table above. The file is overwritten on every call and deleted 60 s after its last write, by the app and by the script itself (from 0.1.13, so the folder stays small when the app is gone); at each launch the app brings an installed script from an earlier version to the current text, DIR written anew, PREV kept; the folder is removed on uninstall.
  • Settings folders: Claude Code reads ~/.claude, or the folder in CLAUDE_CONFIG_DIR. A menu bar app does not see the shell's environment, so the app takes CLAUDE_CONFIG_DIR from its own environment when it has one and looks in the home folder for ~/.claude, ~/.config/claude and folders named .claude-something or .claude_something (the usual way to keep a second account). Install writes the entry into ~/.claude, each CLAUDE_CONFIG_DIR folder, and the other folders only when they hold a settings.json; a folder with only a projects folder (a backup copy) is left out of Install and still counted for transcripts. Each folder has its own script and backup (hook.sh for ~/.claude; for the others a readable name plus a 64 bit FNV-1a hash of the resolved path, so ~/.claude-work and ~/.claude_work never share one), so each chains its own previous command, and all of them write to the one sessions folder. With nothing found, ~/.claude.
  • Installing means editing the user's ~/.claude/settings.json (and each other settings folder's). The app does this only on an explicit click, on "Install the status line entry" on the Claude tab or "Install the status line entry" in Settings. It keeps a previous command by chaining it, keeps the other keys of an existing statusLine object (padding, a user's refreshInterval of 5 or less), sets refreshInterval 5 when there is none or a longer one, and saves the object as it was to statusline-before.json in Application Support. The file is parsed, the statusLine key replaced, and the whole file written back by JSONSerialization pretty printed with slashes unescaped: indentation and key order may change, the content of every other key does not. A file JSONSerialization accepts is taken as JSON, so one with only a trailing comma is read and written back without it. The file is not checked for a change between its read and the write back.
  • Removing is the Settings row "Remove the status line entry", one explicit click. While the entry is still the app's, the saved object goes back exactly as it was, or the key is removed when there was none; an entry the user changed in the meantime is left alone. The script, the saved object and the sessions folder are deleted. settings.json is otherwise off limits; the app reads its modification time each feed tick and reads the file again only when that time moves.
  • Install and Remove write settings.json through a link: when it is a symbolic link (a dotfiles folder), the file it finally names is written, through a temporary file in the same folder renamed over it, with that file's mode. A new settings.json is created 0600. A link is never replaced by a regular file and a mode is never widened. The file a link names is found the way macOS opens it: part by part, a relative link read from the real folder it lies in (a folder on the way may itself be a link), also when the file it names does not exist yet (from 0.1.15, section 20.1; 0.1.11 to 0.1.14 removed .. by text and could name another file). A settings.json over 1 MB or not a regular file is refused with that reason.
  • remove.sh is rewritten at launch, Install and Remove; if it cannot be written, the reason is shown under the Settings row ("Could not write remove.sh, so brew uninstall --zap cannot put your status line back: ...") and logged.
  • An install or remove error is shown under the Settings row, and an Install error also under the button on the Claude tab, wrapped over lines with its reason, and written to the unified log, the message marked private.
  • The entry counts as installed only while the script it points at exists. After brew uninstall --zap without Remove, or a deleted data folder, the app says the script is gone and offers Install again, chaining the command it kept in its preferences.
  • When Install created settings.json, Remove deletes it again if nothing else was added, instead of leaving {}. When that settings.json is a link whose file did not exist before Install (a dotfiles folder), Remove deletes the file Install wrote and keeps the link as the user had it; the app's Remove and remove.sh (through readlink -f) do the same, from 0.1.14. Until 0.1.13 the link went and the entry stayed in the file it pointed at.
  • A .tmp file left by a hook run Claude Code cancelled between the write and the move is deleted 60 s after its last write.
  • tokenpanda --remove-status-line runs Remove in every settings folder and exits. At launch and at every Install and Remove the app also writes remove.sh to the data folder, the same Remove in sh and plutil for the folders whose entry is its own (deleted when there are none). The cask's zap stanza runs that script with /bin/sh before it trashes the data folder, so it works also on Homebrew before 7.0.10, which removes the app before a zap script runs. uninstall runs neither, because uninstall directives also run on every upgrade.
  • The session_id extraction above assumes the key appears as "session_id":"…" without whitespace, as in the capture. When the pattern does not match, the script writes a single latest.json instead; the app parses session_id from the JSON itself, so it reads that file like any other. Nothing else checks the pattern.

The windows: merge, record and staleness

  • Each feed scan, every 5 s and on write events in the sessions folder, reads every snapshot file younger than 60 s. From 0.1.16 a burst of write events is paced (FeedPacer): the first event after a quiet second scans at once, the events that follow within 1 s of a scan become one trailing scan at the end of that second, so the last write is always read, at most 1 s late. A file is parsed again only when its modification time, size or file number changed since the last scan (the hook moves a new file over the old one, so every write changes the file number); an unchanged file keeps its last parse, which gives the same snapshot, so the reply check and the open, live and 60 s rules, which go by the clock, work as before. Claude Code's own session files are read the same way (LiveSessionCache): parsed again only when one changed, the process checked on every scan. The folder watch (FolderWatch) also takes the delete and rename events of the folder itself: then it watches the folder at the same path again, tried every second until the hook script has made it anew, and never makes it itself, so Remove's delete holds; until 0.1.15 a deleted folder left only the 5 s timer until the next start. It hands each event to the main actor from a nonisolated handler; until 0.1.15 the handler itself counted as main actor code running on the timer queue, and the Swift runtime logged a warning for every event. Measured over 3 minutes against a throwaway data folder with 22 synthetic sessions, each rewriting its file about every 0.3 s (about 60 writes a second): 76.6% of one core and at most 50 MB resident in 0.1.15, 2.2% and at most 47 MB from 0.1.16.
  • A file counts for the windows when it carries rate_limits, or when its session replied without them (its token or cost figures moved since the last scan; the first sight of a file after launch is not a reply).
  • Merge (Limits.merge): across those files, per key, the latest resets_at that has not passed, and at that reset the highest used_percentage. The server's figure only rises within a window; a lower one is an older cached reply that an idle session keeps writing. This replaced "the newest file sets the windows" in 0.1.8, which made the weekly figure jump between sessions.
  • Record (Limits.apply), applied only when the newest such file is newer than the stored record, and kept in limits.json. Per key of the merge: a new key is stored as it is; the same reset keeps the higher of the stored and the merged percentage; a later reset after the stored one has passed is the next window of that key, checked against the key's length (below); a reset that moves while the stored window still runs, earlier or later, is another account (/login, or two accounts open at once) and replaces the record without the check.
  • A stored key the scan does not carry is retired, not deleted: until its reset it is drawn quiet, the last percent dim with "not in the last feed", no countdown, pace or projection, no eyes and no nudge. A key missing from a reply that came after that key's reset, or a fixed key (weekly, 5h) never stored and missing from a reply, is hidden, because a reply carries every window the plan has: its row goes (the 5h window of Ultra plans since 30 October 2026). A reply whose rate_limits has no window at all, or that has none (an API key, Bedrock, Vertex), makes the record planless: "these sessions carry no plan limits". A rate_limits with entries none of which read as a window is a changed format: "the feed format changed, update tokenpanda".
  • The record's time is the newest such file's modification time. The header says "Live from Claude Code" while any session file was written in the last 60 s, otherwise "As of HH:MM, last Claude Code session" with the record's time.
  • A record younger than one hour: live. Pace lines are computed.
  • Older than one hour: stale. The bar drops to the track colour, the percent and the notch go dim, "as of HH:MM" replaces the pace lines, the menu bar item dims to 50%, and the Claude tab adds "limits are shared with the Claude app and other Macs, so the real figure may be higher". Nothing is projected from old data. Claude Code itself keeps a 60 minute last known usage when its own request fails; the hour matches it.
  • A window whose resets_at has passed shows an empty bar with "Reset Sun 18:00 no session since"; when it is retired, because sessions still feed and Claude Code dropped the passed window, "Reset Sun 18:00 new window on the next reply". The next reply brings the new window.
  • The first call of a session carries no rate_limits and is not a reply, so it changes nothing; the app keeps the stored values and waits for the next call.

Window length

The feed names its windows and gives resets_at, not a length. The length comes from the key name: five_hour is 5 h, seven_day is 168 h. The start is resets_at minus that length. The app checks the length against the observed distance between two consecutive resets_at values of the same key once it has seen two, and if they disagree, or if a key it does not know appears, it shows the window's percent with "unknown window" in place of the pace lines and never guesses.

4 Open sessions

Every running Claude Code session fires its own feed, so the app knows which sessions are open. One snapshot file per session_id (section 3). A session is open when its file was written in the last 10 s; it leaves the list 60 s after its last write and its file is deleted then.

  • Section "Open sessions" on the Claude tab, after the windows. Two lines per open session. Line one: the session's name in default text, cut with … when name and model would not fit on one line, two spaces, the model's display name dim. The name is the one set with -n or /rename, read from Claude Code's own session file (<settings folder>/sessions/<pid>.json, on every feed scan, whatever the settings; only when nameSource is user); without one, the project folder's last path segment; without that, the session id's first eight characters. Line two: a 24 cell plain bar of context_window.used_percentage in the hue of the model's family, two spaces, the context figure "405.6k of 1M" and the percent "41%". No notch: the context is a share, not a time window.
  • The figure's tooltip: "USD 38.20 list price equivalent 112 added 9 removed", from cost.total_cost_usd, total_lines_added, total_lines_removed; " effort high" is appended when effort.level is present. A long tooltip breaks over two lines inside the panel.
  • The context figure is current_usage's four counts summed, formatted as k or M, over context_window_size formatted as k or M ("1M"). When current_usage is null (first call), the bar line is replaced by "waiting for the first reply" dim; when it is null and the session's cost is above zero (after /compact or a resume), by "compacted or resumed next reply updates it".
  • Sorted by context used, largest first; at most five, then "and N more" dim.
  • No open session, stale figures included: the title stays with "no open session" dim under it. The section is left out only in the No hook state (section 14).

Not available by the rules and never drawn: the context breakdown by category (messages, system tools, memory files, skills, MCP) and the per MCP tool token counts that Claude Code shows in its own usage screen. Those are computed inside Claude Code and are in neither the feed nor the transcripts.

Working sessions and keep awake

  • An open session is working while its figures move: current_usage summed, total_cost_usd, total_lines_added, total_lines_removed and used_percentage. The app remembers per session when they last changed; a session counts as working for 10 minutes after that (Rules.keepAwakeGrace). The first snapshot of a session counts as a change. An idle session writes the same figures every 5 s, and a repeat is not a change, so an idle terminal does not count. A session that leaves the open list is forgotten.
  • With the setting keepAwake on and at least one session working, the app holds one IOKit power assertion, IOPMAssertionCreateWithName with kIOPMAssertionTypePreventUserIdleSystemSleep, named "tokenpanda: Claude Code is working". The display may still sleep. Never a second assertion while one is held. Released as soon as no session works, when the setting is turned off, and when the app quits. pmset -g assertions shows it.
  • With the second setting keepAwakeWhileOpen on as well, any open session holds the same one assertion, idle or working, for Remote Control from the phone: a session waiting for a prompt keeps writing every 5 s, so it stays open (the 10 s rule above) and needs no grace. The assertion is then named "tokenpanda: a Claude Code session is open"; when the reason changes, the held one is released before the one with the other name is made. keepAwakeWhileOpen counts only while keepAwake is on.
  • Limits, said plainly: it prevents idle sleep only, so a closed lid on battery still sleeps the Mac. A single step that runs longer than 10 minutes without moving the figures lets the Mac sleep as usual.

5 The transcript reader

Paths

  • ~/.claude/projects/<project>/<session>.jsonl for a session; ~/.claude/projects/<project>/<session>/subagents/agent-<id>.jsonl for its subagents (a sibling agent-<id>.meta.json is not read). The project folder is the absolute working directory with every slash replaced by a dash. The session id is the file name without .jsonl; every line inside carries sessionId equal to it.
  • Also ~/.config/claude/projects, the directories in CLAUDE_CONFIG_DIR when set (ccusage reads these; comma separated), and the projects folder of every settings folder of section 3, a .claude-something backup with only a projects folder included.
  • Only *.jsonl at depth 1 under a project and under subagents/. Files modified in the last 32 days; the windows need 30.
  • Documented retention: "Claude Code clients store session transcripts locally in plaintext under ~/.claude/projects/ for 30 days by default to enable session resumption. Adjust the period with cleanupPeriodDays." So the 30 day figure depends on that setting. No published schema; one session file can mix Claude Code versions (2.1.278 to 2.1.294 in one file); the parser skips any line it cannot read.
  • Streaming, line by line: one file on the build Mac was 371 MB and 40483 lines. Never load a whole file. A single line over 10 MB is skipped up to its newline without being held whole, also across reads. A line whose token counts are negative or past 2^40 is skipped, and the sums saturate instead of trapping.

  • ~/.claude/projects/<project>/memory/: personal notes in Markdown. Not transcripts.
  • ~/.claude/projects/<project>/<session>/tool-results/: tool outputs and hook output with file contents, images and PDFs.
  • <session>/custom-title.json, auto-mode-classifier-error.txt, the agent-<id>.meta.json files.

One folder there is read, as the privacy page says: Claude Code's own session files, <settings folder>/sessions/<pid>.json, on every feed scan, whatever the settings, for the session names under Open sessions (section 4) and, with Reopen on, for the folder and the process to reopen (section 10). The keys used: sessionId, pid, procStart, kind, entrypoint, cwd, and name with nameSource; the rest of the file is dropped. A file of 64 KB or more, or not a regular file, is skipped before it is read, and a file whose process no longer runs is ignored. From 0.1.16 a file whose procStart (the process start as ps -o lstart prints it in UTC with the C locale, read 05.11.2026) is more than 2 s off the process's own start time (kinfo_proc p_starttime) is ignored too: the pid now belongs to another process. A file without the key, or a process whose start cannot be read, is judged by the pid alone, as before. These files are not documented by Anthropic; without them a session shows its folder.

The reader enumerates only the two patterns in "Paths" and never walks a directory recursively.

Dedupe

Claude Code writes one assistant line per content block (thinking, text, tool use), each carrying the same message.id and the same usage. On the build Mac: 5926 assistant lines for 3679 distinct ids, one id up to eleven times; the naive sum of output_tokens was 2.45 times the true figure. Rule: keep the first line per message.id and skip the repeats, per file; the usage is identical across repeats. The seen ids live with each file, so an id repeated in another file of the same session (a resumed or forked session, if Claude Code copies earlier lines) would count again; whether that happens is settled by neither a source nor a test. message.id and requestId are one to one (3679 of each), so the request id is a cross check only.

Reading cadence

  • Full pass on launch and every 300 s. Files modified since the last pass are read from their last byte offset every 10 s while the popover is open.
  • The aggregate is rebuilt when a record was added, and from every record on the first pass and on the first pass of a new day, because "today" and "7 days" move with the date while no file changes (TokenRefresh.needsAllRecords, from 0.1.14), and from 0.1.15 also on the first pass after the oldest record inside the 7 or 30 day window has left it (section 20.2). Until 0.1.13 the first pass after midnight summed no records, and every token row read "nothing in the last 7 days" until the next transcript write.
  • On an actor off the main thread; the UI gets a finished aggregate.

7 The pace model

Four inputs per window: used percentage U, window start S (resets_at minus the length named by the key), reset R, now T.

elapsed    = T - S                       (hours)
remaining  = R - T                       (hours)
E          = elapsed / (R - S) × 100     (elapsed share, percent)

status     = Over pace  when U > E + 5
             Ahead      when U < E - 5
             On pace    otherwise

rate       = U / elapsed                 (percent per hour)
to_limit   = (100 - U) / rate            (hours)
projection = if E < 5 and status is not Over pace:  "too early to project"   (from 0.1.15, section 20.7)
             if to_limit < remaining and status is Over pace:  "limit " + clock(T + to_limit) + " at this rate"
             else:                      min(100, round(U + rate × remaining)) + "% by reset at this rate"
allowance  = (100 - U) / remaining       (percent per hour) + "% an hour left"
countdown  = remaining as "in Nd Nh" or "in Nh Nm"
  • The projected clock time is rounded to five minutes; the weekly form carries the weekday, the 5h form does not.
  • The allowance prints one decimal under 1% and whole numbers from 1%.
  • The tick on the bar, the two cell notch ▐▌ of the style guide, stands at E. The fill past the tick is coral only when the status is Over pace.
  • Stale windows compute nothing; a window with U = 0 has no rate and prints no projection; an unknown window (section 3) prints "unknown window".

Intervals and budget

  • Popover open: every 2 s, all figures, the process table included. Measured: sampling everything every 2 s, every process' rusage included, costs 0.40% of one core (getrusage(RUSAGE_SELF) over 60 s, 4.5 to 5.1 ms per sample).

  • Timers are DispatchSourceTimer on a utility queue with a leeway of 10% of the interval.

The Mac warning rule

Memory pressure warn or critical, or one process over 80% CPU for 60 s, timed by the clock from the first sample that saw it, so the rule is the same at the 2 s and the 10 s cadence. While it holds: the Mac tab gets the ● dot, the menu bar item appends ⚠. The Mac figures themselves stay off the menu bar unless the setting is on.

Reopen sessions after a restart

  • Off by default. While it is on, every feed scan puts the open sessions (id, workspace.project_dir or cwd, transcript_path, name, start options) into restore.json, mode 0600, written when a session comes or goes or a name or the options change. A session stays on the list for ten minutes after its last feed, because at a restart the terminal app closes the sessions before the app quits.
  • At launch, before the first scan: if the record's last scan is before kern.boottime and not more than seven days old, the sessions seen within ten minutes of that scan are offered.   • Reopen skips sessions that are open again, waits for the network the same way, then deletes the Reopen folders (tokenpanda-reopen-*, real folders only, directly in the app's temporary folder) last changed more than 10 minutes ago, as it does at launch, and writes one script per session into a new 0700 folder in the temporary folder (file 0600, then 0700, so only you can read or run it): rm -f -- "$0", rmdir -- "${0:h}" 2>/dev/null (the last script takes the folder with it), cd to the quoted folder, claude --resume with the quoted id, the kept options and --name, and --remote-control when the transcript holds a "type":"bridge-session" line; a start that exits non zero within 20 s falls back to the same without Remote Control, then a plain resume; at the end exec "$SHELL" -l, so the window keeps a shell.   • Session ends: each scan compares the running sessions by process. Path one: unsigned (ad hoc), own tap

Ad hoc signing does not satisfy Gatekeeper on a downloaded file, and since macOS Sequoia Control-click no longer overrides it. Apple's current page (published 2026-05-27) gives the flow, which the README repeats:

  1. Try to open the app.
  2. Open System Settings, click Privacy & Security, scroll down, and click the Open Anyway button.
  3. The warning reappears; click Open. The app is now saved as an exception and opens by double click from then on.

Apple's page names Catalina and later and Sequoia; it does not name macOS 26 or 27, so it is Apple's current page rather than a version specific statement. Removing the quarantine attribute with xattr is a community workaround and is not in the README.

Homebrew's main cask repo requires that artefacts "must pass Homebrew's Gatekeeper checks", and support for failing casks ended on 2026-09-01, so an unsigned app lives in its own tap: the repository tokenpandadev/homebrew-tap, with a Casks directory at the top level holding tokenpanda.rb (the template is in this repository under Casks/); users run brew trust --cask tokenpandadev/tap/tokenpanda, then brew install --cask tokenpandadev/tap/tokenpanda, as the README says. No notability rule applies to a tap; "Non-official taps require explicit trust by default". The Open Anyway flow still applies after a brew install.

Path two: Developer ID and notarisation

  • Apple Developer Program, 99 USD a year, includes the Developer ID certificate; no fee waiver for an individual.

Stapled, Gatekeeper needs no online check and the user sees no warning.

20 Changes in 0.1.15

The open findings of the release audit of 0.1.14 (F-1 to F-5) and two friction steps of the 0.1.14 flow test (04.10, 06.8), each as numbered cases. Every installed version is read with git show v0.1.14:<path>; nothing here changes a file format, the hook script or remove.sh.

20.1 A link is followed the way macOS follows it (F-2)

0.1.11 to 0.1.14 (SettingsFile.resolve) joined a relative link to the folder of the path as written, then removed .. by text. When a folder on the way is itself a link, macOS counts .. from the real folder, so the two named different files while the target did not exist yet. Install then wrote the entry into that other file (whole, since a missing settings.json starts empty), said installed, and the status still said not installed. From 0.1.15 the path is walked part by part from /: each part that is a link is replaced by its target, an absolute target from /, a relative one from the real folder reached so far; .. steps up from that real folder; a part that does not exist ends the walk with the rest appended. More than 32 links is a loop.

  1. 20.1.1 ~/.claude is a link to dotfiles/claudedir, settings.json in it a link ../dotfiles/claude.json, missing (the audit's caseA, the verifier's V2). The file named is dotfiles/dotfiles/claude.json, as readlink -f and Claude Code see it, and dotfiles/claude.json, a file of the user's, is not touched. The folder dotfiles/dotfiles does not exist, so Install writes nothing and says so (20.1.9); once the user makes the folder, Install creates the file and the status says installed.
  2. 20.1.2 The same linked ~/.claude, settings.json a link ../claude.json, correct for the real folder, its target not made yet (the verifier's V1). The file named is dotfiles/claude.json; a claude.json in the home folder is not touched.
  3. 20.1.3 Remove, in the app and in remove.sh, after Install in both layouts: the entry goes from the file Install wrote, that file is deleted when Install created it and nothing else is in it, and the link stays.
  4. 20.1.4 The layouts that worked keep working: an absolute link, a relative link with no linked folder on the way, a link whose target exists, a chain of two links, a missing settings.json in a real folder, and a loop, which throws. The resolver names the same file as realpath wherever the target exists.
  5. 20.1.5 Already installed by 0.1.11 to 0.1.14 in one of these layouts: the status said not installed, so Install is offered again and writes the right file. A file written at the wrong path by those versions is not found or repaired; the app cannot tell it from the user's own.
  6. 20.1.6 After a part that does not exist, .. cannot be followed: the kernel answers ENOENT, and so does the resolver, so Install reports the error and writes nothing. (settings.json a link nodir/../other.json with other.json next to it: the kernel opens nothing, a text resolver named other.json.)
  7. 20.1.7 Only a part that is not there (ENOENT) counts as missing. Any other error on the way, a part that is a file and not a folder (ENOTDIR) or a folder that cannot be read (EACCES), is thrown, as the kernel would fail the open.
  8. 20.1.8 The link limit is the kernel's: 32 links on the way resolve, the 33rd is a loop (ELOOP), counting a linked folder such as /tmp.
  9. 20.1.9 Install makes a missing folder only when it is the settings folder itself and no link (a missing ~/.claude, as Claude Code makes it). A settings.json that is a link into a folder that does not exist, or a settings folder that is a link to one, is refused before anything is written (no script, no backup, no remove.sh), with "cannot write settings.json: it is a link into ~/dotfiles/dotfiles, a folder that does not exist"; Claude Code's own write there would fail too. 0.1.11 to 0.1.14, and 0.1.15 before its audit (F-6), made that folder and its parents, and Remove left them. Removing the folders again on Remove was the other way; it is not taken, because the app would then delete folders in the user's dotfiles.

20.2 The 7 and 30 day rows move at their edge (F-3)

The windows roll from now (section 5), but the aggregate was built again only with a new record or a new day, so on a quiet day the rows kept up to a day of records past their edge. From 0.1.15 TokenSummary.nextEdge keeps the earliest time a record leaves the 7 or 30 day window (or a record dated after now enters), and the first pass after it builds the aggregate from every record again.

  1. 20.2.1 A record 7 days less 1 hour old, no new line: two hours later the 7 day rows (totals, by model, by project, agent share, list price) no longer count it, the 30 day total still does.
  2. 20.2.2 A record 30 days less 1 hour old, no new line: two hours later the 30 day total no longer counts it.
  3. 20.2.3 No record at an edge: a pass on the same day with no change still asks for changes only and keeps the aggregate (the 0.1.14 rule and its midnight test stand).
  4. 20.2.4 The windows are lengths of time (7 and 30 times 24 hours), not calendar days: across a change to or from summer time the edge is the record's time plus that length, and the "today" rows still start at local midnight.

20.5 VoiceOver scrolls a capped panel (F-5)

macOS 14 and 15 have no public scroll to visible action an element can take; NSAccessibilityScrollToVisibleAction is declared from macOS 26, without a method in the NSAccessibility protocol, so only the deprecated accessibilityPerformAction would receive it, and the app does not use deprecated API. What is public on every version is the focus: VoiceOver moves the keyboard focus with its cursor ("keyboard focus follows the VoiceOver cursor", on by default) by setting the accessibility focus of an element that allows it.

  1. 20.5.1 Every element of the panel, text lines and groups as well as controls, allows setAccessibilityFocused. For a text line or a group it scrolls the line into view with one line of room and moves no keyboard focus; for a control it does what it did, the keyboard focus and its ring, scrolled into view.
  2. 20.5.2 A line already in view does not move the panel.
  3. 20.5.3 to be verified: that VoiceOver sets the focus on a text line as it moves onto it; the testing page, section 5, checks it on a capped panel. If it does not, the outline stays outside the visible part for text lines, as in 0.1.14.

20.6 A nudge is spent only when it was posted (flow test 04.10)

Until 0.1.14 the window was marked nudged right after the post was asked for, whatever came of it: a nudge due while notifications were off was spent, and after they were turned on it never came for that window. From 0.1.15 the rule is NudgeRules.due (tested on its own) and NudgeLedger gives each window its nudge once: it asks for the permission, checks the rule again with the clock and the feed of that moment, marks the window, posts, and takes the mark back when the post was refused. One post per window is on its way at a time; a window is the key and its reset together, so a pending post never blocks the next window.

  1. 20.6.1 Notifications off, the weekly nudge due: nothing is posted and the window is not marked.
  2. 20.6.2 Turned on again in the same window: the next check (each feed pass while a session feeds; the settings are reread at most once a minute while notifications are off, so within about a minute) posts the nudge once, with the figure of that moment ("Weekly at 87%"), and marks the window. It comes only while its rule still holds: the weekly at 80% or more, the feed fresh, before the reset; the 5h nudge only inside its last 15 minutes. A window that has passed is never nudged late.
  3. 20.6.3 While a post is on its way (the prompt is up, or the centre has not answered), a second check does not post again; a post that fails leaves the window open for the next check.
  4. 20.6.4 A window marked by an earlier version stays marked; the mark's format does not change.
  5. 20.6.5 The rule is checked again after the permission is known: a first prompt left unanswered past the end of the 5h window posts nothing when it is answered, and the window is not marked. The next window has its own nudge, also while the old one's post is still waiting.
  6. 20.6.6 The window is marked before the post goes out and the mark is taken back if the post is refused, so an app quit between the post and the mark never posts the same window twice after the next launch.
  7. 20.6.7 While notifications are off the permission is read again at most once a minute, and at each open of the panel, not at every feed pass; turned on in System Settings, the held nudge comes within about a minute, or at once when the panel is opened.
  8. 20.6.8 The rule itself: Nudge ticked; the feed younger than the stale limit; the weekly at 80% or more and before its reset, not retired or hidden; the 5h window only from 15 minutes before its reset until the reset.

20.7 No projection from the first minutes of a window (flow test 06.8)

The projection is the used share over the hours elapsed, with no minimum, so the first reply of a week (2% half a minute in) read "On pace limit Wed 10:35 at this rate", a limit 22 minutes away under "On pace". Rule and texts, approved on 2026-11-04:

  1. 20.7.1 Until 5% of the window has passed (8 h 24 min of a week, 15 min of a 5h window), the projection shows only when the status is Over pace. Otherwise the line reads "On pace too early to project" (or "Ahead too early to project"), and VoiceOver says "On pace, too early to project" (tested on the window's spoken label). The weekly nudge body names no projection in that phase.
  2. 20.7.2 "limit ... at this rate" shows only when the status is Over pace. On pace or Ahead the line always reads "N% by reset at this rate", N at most 100: 57% at 55% of the week reads "On pace 100% by reset at this rate" (was "limit Sun 12:00 at this rate").
  3. 20.7.3 Over pace keeps today's text in every phase: 10% ten minutes into a 5h window still reads "Over pace limit 15:50 at this rate".
