1 The short version

This app makes no network calls. Usage comes from Claude Code's own status feed on this Mac.

That is the sentence in the app's Settings, and it is the whole policy. Everything below spells it out: what the app reads, what it keeps, and what leaves your Mac, which is nothing.

2 What the app reads

The status line feed

While a Claude Code session is open, Claude Code runs a small script every few seconds and hands it a JSON object. The app installs that script, with your permission, and the script copies the object to a file. The app reads these fields from it and nothing else:

  • the two plan windows: how much of the 5 hour window and of the weekly window you have used, in percent, and when each resets
  • which session this is (its id), which folder it runs in, which model it uses and at what effort level
  • how full the session's context window is, and its running cost at list price, lines added and lines removed, as Claude Code itself reports them

The object also carries other things, like the path of the session's transcript and cache statistics. The app ignores them. The object contains no password, token or key; it is paths, numbers, model names and ids.

The transcripts

Claude Code keeps a transcript of each session on your Mac, in plain text, under ~/.claude/projects, for 30 days by default. The app reads those files to count tokens. From each line it takes only: the line type, the time, the message id, the request id, whether the line came from a subagent, the session id, the working directory (cwd), the model id, and the five token counts. It does not read what you wrote, what Claude answered, which files were opened or what the tools returned. Those parts of each line are dropped before anything is kept.

The project name you see is the last folder of that working directory; when a line carries none, it is the last part of the project folder's name, which Claude Code builds from the same path. Only that last folder name is kept, in memory. The session you see is the file's name, which is an id.

Your Mac

The second tab shows CPU, GPU, memory, battery and the busiest processes. These come from the same public system calls Activity Monitor uses. They are sampled every 2 seconds while the popover is open and every 10 seconds while it is closed, kept in memory, and never written to disk.

3 What it never reads

The folder that holds the transcripts also holds things that are not transcripts. The app never opens them. This is a rule in the code and a test in the test suite, not a promise:

  • ~/.claude/projects/<project>/memory/: personal notes Claude Code keeps across sessions
  • ~/.claude/projects/<project>/<session>/tool-results/: tool outputs with file contents, images and PDFs
  • title files and error files next to a transcript, and the subagent metadata files
  • anything else in ~/.claude: history, stats caches, sessions, state, uploads, the daemon, the paste cache, file history
  • your settings.json, except the one status line key the app edits when you ask it to (section 7) and disableAllHooks, which it reads to say when Claude Code runs no status line
  • in your home folder the app lists names only, to find Claude Code's settings folders: ~/.claude, ~/.config/claude, the folder in CLAUDE_CONFIG_DIR and folders named .claude-something or .claude_something; it checks whether they hold a settings.json or a projects folder and opens nothing else there
  • inside a transcript line: the message content, the tool results, attachments, snapshots and the account ids

For each running session the app also reads Claude Code's own small session file (~/.claude/sessions/<process id>.json, and the same in each other settings folder: session id, folder, name, and the process's start time, checked against the process table so a file a session left behind is not taken for a session when its process number is used again), to show the session by its name under Open sessions; without the file a session shows its folder. With "Reopen sessions after a restart" on, it also reads the options the session's process was started with (from the process table, KERN_PROCARGS2, arguments only, not its environment). It keeps the name and the options that set the session up, and leaves out a start prompt and the options that pick or fork a session. That session file is not documented by Anthropic; without it, sessions still reopen, with a plain resume.

One exception, only with "Reopen sessions after a restart" on and only when you click Reopen: the app looks in each offered session's transcript for the line Claude Code writes when Remote Control was on ("type":"bridge-session"), to know whether to start that session with Remote Control again. The path comes from the feed, so the app opens it only when it is a regular file. It checks that the line is there and reads nothing from it.

Two things Claude Code shows in its own usage screen are not in the feed and not in the transcripts, so the app does not show them and does not try to work them out: the breakdown of a session's context by category (messages, system tools, memory files, skills, MCP servers) and the token count per MCP tool. Those are computed inside Claude Code.

The app never reads the Keychain. It never reads the Claude Code credential item, a token, a cookie or a session key. It never asks you to sign in.

4 What it writes

  • ~/Library/Application Support/dev.tokenpanda.app/sessions/<session id>.json: the latest status line object of each open session, overwritten every few seconds and deleted a minute after the session stops feeding
  • ~/Library/Application Support/dev.tokenpanda.app/hook.sh: the status line script; with more than one settings folder, one more script per folder, hook-<folder>-<hash>.sh
  • ~/Library/Application Support/dev.tokenpanda.app/remove.sh, while the entry is installed: the Remove step as a shell script, which brew uninstall --zap runs; it lists the settings files and the saved entries, nothing else
  • ~/Library/Application Support/dev.tokenpanda.app/statusline-before.json: your statusLine entry as it was before the install, so removing the hook can put it back exactly; deleted on removal
  • ~/Library/Application Support/dev.tokenpanda.app/limits.json: the last two plan windows (used percent and reset time) and the time they were read, so the figures outlive the session files; no path, no model, no session id
  • ~/Library/Application Support/dev.tokenpanda.app/weeks.json: four small records of past weekly windows, for the week over week rows
  • ~/Library/Application Support/dev.tokenpanda.app/restore.json, only with "Reopen sessions after a restart" on: the open sessions' ids, folders, transcript paths, names and start options, and when each was last seen, readable only by you; deleted when you turn the switch off. The start options are copied as given, so an appended system prompt passed on the command line is in the file in full.
  • when you click Reopen: one small script per session in a private folder in your temporary folder, readable only by you, which Terminal, iTerm or Ghostty runs (the one picked under "Open sessions in") and which deletes itself as it starts, the last one its folder too. When you cancel Ghostty's prompt for a script, that script stays until the app deletes Reopen folders older than ten minutes, at the next Reopen or the next start of the app
  • your preferences in the app's preferences file under ~/Library/Preferences: six switches, the app Reopen opens sessions in (Terminal, iTerm or Ghostty), two timestamps the nudges use, the flag that the hidden icon window was shown, and, from Install until Remove, the status line command and refresh interval you had before, so Remove can put them back even when the backup file is gone

No log file. No cache of transcripts. No copy of anything you wrote. If installing or removing the hook fails, the error is shown in Settings and written to the macOS unified log, with the message marked private. A failed write of remove.sh, limits.json, weeks.json or restore.json goes to the same log, the path and the reason marked private; when remove.sh cannot be written, Settings says so too, because brew uninstall --zap needs it to put your status line back.

Files other programs write are read with limits: a status line object or a settings.json over 1 MB, or a Claude Code session file over 64 KB, is skipped before it is read, and only regular files are opened. A transcript line over 10 MB is skipped. Numbers out of range in any of them are ignored.

With "Keep the Mac awake while Claude works" on, the app holds one power assertion against idle sleep, and only while a Claude Code session is working, which means its figures moved in the last ten minutes. With the second switch under it, "also while a session waits for you", it holds the same one assertion while any session is open, idle ones too, so a session stays reachable through Remote Control from the phone. It writes no file for this; pmset -g assertions in Terminal shows it as "tokenpanda: Claude Code is working" or "tokenpanda: a Claude Code session is open" while it is held. The display may still sleep, and a closed lid on battery still sleeps the Mac: this keeps it from idle sleep only.

With "Open at login" on, the app asks macOS to open it at login through the system's own login item service (SMAppService), only when you click the row. The app writes no file for this and keeps no setting of its own: macOS keeps the record, System Settings, General, Login Items lists it, and you can remove it there. Clicking the row again removes it.

With "Reopen sessions after a restart" on, the app notes which Claude Code sessions are open, from the same status line feed, and keeps a session on the list for ten minutes after its feed stops, because at a restart the terminal app closes the sessions before the app quits. After the Mac starts again, one notification names them, once the Mac has a network address (the app reads the network interfaces' state; it opens no connection). Nothing starts on its own. Only a click on Reopen starts the picked app (Terminal, iTerm or Ghostty), with one window per session that is not open already (in Ghostty, one tab per session in its window): cd into the session's folder, then claude --resume with the session id, its start options and its name, and --remote-control for sessions that had it; if that fails within 20 seconds, the same without Remote Control, then a plain resume. When a session ends, the window keeps a shell. A session that ends while the process that started it still runs (its window's shell) gets one notification with its name and a Reopen button for that session; when the window closed too, or the Mac shuts down, there is none. Session ids are checked to be ids and folders to exist before anything is written, and both are quoted for the shell. The picked app opens the scripts the same way a double click would, so the app needs no permission to control it. The steps (how many sessions were offered and reopened, no ids or paths) go to the macOS unified log, and so does a script the picked app could not open, the reason marked private.

5 What leaves your Mac

Nothing. The app has no network code. It does not check for updates, does not fetch prices, does not send crash reports, does not send usage statistics, and does not call any Anthropic endpoint. The prices it uses for the "list price equivalent" figure are a table inside the app, updated with releases.

Updates come from the project's GitHub releases or from Homebrew when you ask for them.

The app carries a privacy manifest (PrivacyInfo.xcprivacy in the app's Resources folder), as Apple asks of apps: no tracking, no data collected, and why it calls the system for file dates, the boot time and its own preferences.

6 Your account

The app has no account, no sign in and no access to yours. The plan percentages it shows are the ones Claude Code already knows and hands to its status line. They cover your whole account, so use of Claude on the web or in the apps moves them too; the app says so when it shows figures from a past session.

7 The hook and your settings

To get the feed, Claude Code has to be told to run the app's script. That is one entry, statusLine, in ~/.claude/settings.json, and in the settings.json of each other settings folder Claude Code uses on this Mac (a CLAUDE_CONFIG_DIR folder for a second account, for one). The app does not write it on its own. It edits the file only when you click "Install the status line hook" on the Claude tab or "Install the status line entry" in Settings. If you already have a status line, the app keeps it: the script passes the same data on to your command and shows its output, so your status line looks the same as before. Inside your statusLine entry only type and command change; other keys such as padding stay. refreshInterval is set to 5 when there was none or a longer one, so open sessions stay listed; a shorter one of your own stays, and Remove puts your own value back.

"Remove the status line entry" in Settings undoes it with one click: your previous statusLine entry goes back exactly as it was, or the key is removed if there was none. If you changed the entry yourself after installing, removing the hook leaves your entry alone. Either way the script, the saved entry and the sessions folder are deleted. If the install created settings.json and nothing else was added to it since, the file goes too.

The file is read and written whole by the macOS JSON writer, so its indentation and the order of its keys may change when the app writes it. In content, only the statusLine key differs. The app otherwise only checks the file's modification time, to notice when the entry changed. If settings.json is a link, into a dotfiles folder for one, it stays a link: the app writes the file it points at, in one step, and keeps that file's permissions. A settings.json the app creates is readable by you only.

8 How to check

  • The source is public. Search it for URLSession, Network, http or Security: there are none.
  • Run a network monitor such as Little Snitch, or nettop in Terminal filtered to the app, for an hour: zero connections.
  • Open the sessions folder in Application Support and read a snapshot file: it is the status line object Claude Code produced, as is.
  • Open ~/.claude/settings.json and read the statusLine entry: one script path and a refresh interval.
  • Open System Settings, General, Login Items: the app is listed there only while Open at login is on.
  • Open restore.json in Application Support while Reopen sessions is on: ids, folders, transcript paths, names, start options and times, nothing else.
  • Run pmset -g assertions: the app appears there only while keep awake is on and a session works, or with the second switch, while a session is open.

9 Removing the app

  1. In the app's Settings, click "Remove the status line entry". Or remove the statusLine entry from ~/.claude/settings.json yourself.
  2. If Open at login is on, click it off in Settings, or remove the app in System Settings, General, Login Items.
  3. Quit the app and move it to the Bin, or brew uninstall tokenpanda. brew uninstall --zap tokenpanda does step 1 by itself, then the deletes of step 4.
  4. Delete ~/Library/Application Support/dev.tokenpanda.app and ~/Library/Preferences/dev.tokenpanda.app.plist.

Nothing else was created.

10 What Anthropic says

Anthropic's documentation describes the status line feed as input for any shell script you configure. Its legal page bars third party apps from collecting, storing or passing on Claude.ai credentials or session tokens; this app does none of that. Anthropic has written nothing either way about a local tool reading the transcripts on your own Mac. That is silence, not permission, and this page says so rather than claiming more.
