6 How it is done

Before every release, in this order:

  1. Scope: the commit, the last audited tag, and what the app exposes. tokenpanda has no network listener and makes no network calls; it reads Claude Code's status line feed, the transcripts and settings.json, and writes its own data folder and, on a click, one key of settings.json.
  2. Scanners, as in section 5.
  3. An AI agent reads the code against every requirement in scope and sets pass, fail or does not apply, with evidence. A full audit covers every requirement at Level 2; a release audit covers every requirement the change touches, and the rest keep their result from the audit before.
  4. A second AI agent, which did not write the findings, checks each one again in the code and by experiment, re-checks a sample of the passes, and confirms, changes or drops each finding.
  5. The release gate: no release with an open blocker or high finding, or with any open finding that users may notice, unless the maintainer decides otherwise in writing. Those decisions are marked accepted above.

Next to ASVS it checks our own list, grouped by the ISO/IEC 25010 quality characteristics (stability, reliability, maintainability and the rest), and platform checks for a Mac app: signing, notarisation, the hardened runtime, entitlements, Apple's interface guidelines, accessibility and the privacy manifest. Those checks are ours and are named as ours; ISO's own text is not quoted.

What this does not give: AI agents can miss things a person would find, and nobody outside the project has checked this work. If you find something, the security advisory form reaches me privately.
