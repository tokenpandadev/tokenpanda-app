3 Fixed and accepted

F-70 A copy of the settings folder kept as ~/.claude-something doubles every token figure: duplicate replies are skipped per file only

medium fixed users may notice it

Requirements: Q-FUN-3

Where: Sources/Feed/Hook.swift:651-653

What was found: ConfigFolders takes every ~/.claude- or ~/.claude_ folder that holds a projects folder as a transcript folder (Hook.swift:651-653, 657-661; the comment at Hook.swift:606-608 names ~/.claude-backup as such a folder), and the Controller makes each one a transcript root (Sources/App/Controller.swift:99-104). The store keeps seen message ids per file (Sources/Transcripts/Store.swift:179) and the 0.1.19 inode check catches only links (Store.swift:59, Sources/Transcripts/Locator.swift:49); the summary sums every record (Sources/Transcripts/Aggregator.swift:75-95). Probe in the throwaway copy: one assistant line of 150 tokens in ~/.claude/projects and the same file copied into ~/.claude-backup/projects gave 2 files, 2 records, tokens7d 300. README.md:61 tells users such a backup copy is left out, which holds for Install only. The spec says dedupe across files is settled by neither a source nor a test (docs/spec.html:226).

The fix: Skip a message id already counted in any file (one set across the store, message id plus request id), or read a transcript only folder only when it holds a settings.json, as Install does, and say so in the README.

The verifier: fixed at f176c91: a ~/.claude-* folder counts for transcripts only with a settings.json, and each message id is counted once across files; tests in SettingsBytesTests; confirmed by the final review (the 2026-11-11-full-pass audit).

F-71 remove.sh rewrites settings.json in place: a write that fails part way leaves the user's file truncated

medium fixed users may notice it

Requirements: V2.3.3, Q-REL-4, Q-SAFE-2

Where: Sources/Feed/Hook.swift:800

What was found: The zap path writes the edited text with printf '%s\n' "$OUT" > "$T" (Hook.swift:800): the shell truncates settings.json first, then writes. The app's own writer uses a temp file in the same folder, fsync and rename (Hook.swift:569-598), and the plutil path it replaced is not used when the JavaScript edit succeeds. Shown in this audit on a throwaway 2108 byte settings file with the zap program and the same printf line under a file size limit: the file was left at 512 bytes and no longer parsed as JSON. brew uninstall --zap runs this for every settings folder (Casks/tokenpanda.rb:26-31).

The fix: Write to a temp file next to the target, copy the target's mode to it, then mv -f it over the target (the same rule as SettingsFile.write); leave the target alone when printf fails.

The verifier: fixed at f176c91: remove.sh writes a temporary file next to the target, checks it and renames it over; a failed write says the entry is still there and exits 1; confirmed by the final review on read only files, links and odd paths.

F-72 remove.sh changes bytes outside the statusLine member: the end of the file and the restored entry's layout

low fixed users may notice it

Requirements: Q-FUN-2

Where: Sources/Feed/Hook.swift:799-800

What was found: Command substitution drops every trailing newline of the edited text and printf adds one (Hook.swift:799-800), so a file without a final newline gains one and a file ending in blank lines loses them (shown in this audit: '}' became '}\n', '}\n\n\n' became '}\n'). When an earlier entry is put back, the whole member is replaced by JSON.stringify(j,null,2) as plutil extracts it from the backup (Hook.swift:797, 410-411), not in the user's spacing: in a file indented four spaces the restored entry's keys stood six spaces deep instead of eight. docs/spec.html 24.18 and docs/privacy.html:107 say every other byte stays; the app's own Remove edits the entry member by member and keeps them (Hook.swift:340-342).

The fix: Have the JavaScript return the text with an end marker and print it without adding a newline; put a saved entry back member by member as SettingsText.changes does, or say in the privacy page that the zap may respell the restored entry.

The verifier: fixed at f176c91: the zap keeps the final line break and puts a saved entry back in the file's own layout; confirmed by the final review (4 space, tab CRLF, compact BOM).

F-73 When some sessions of a Reopen click cannot be opened and at least one can, nothing tells the user about the others

low fixed users may notice it

Requirements: Q-INT-2

Where: Sources/Feed/Launch.swift:471

What was found: nothingOpened returns nil as soon as one script was written (Launch.swift:470-471), so the notice is posted only when every session failed (Sources/App/ControllerRestore.swift:198-200); the skipped ones go to the log only (ControllerRestore.swift:194-197). A user who clicks Reopen for three sessions, two of whose folders are gone, gets one window and no word. The spec chose this (docs/spec.html 24.12, test oneGoneOneThereOpensOneAndTellsNothing), but the first audit's fix for F-53 asked for one notice naming the sessions that did not reopen.

The fix: Post one notice for the skipped sessions also when others opened, for example '2 of 3 sessions did not reopen: their folders are gone'; wording shown to him first.

The verifier: fixed at f176c91: ReopenWrite.notice names how many did not reopen and why, and how many did; privacy page and README say so (28331c1).

6 How it is done

Before every release, in this order:

  1. Scope: the commit, the last audited tag, and what the app exposes. tokenpanda has no network listener and makes no network calls; it reads Claude Code's status line feed, the transcripts and settings.json, and writes its own data folder and, on a click, one key of settings.json.
  2. Scanners, as in section 5.
  3. An AI agent reads the code against every requirement in scope and sets pass, fail or does not apply, with evidence. A full audit covers every requirement at Level 2; a release audit covers every requirement the change touches, and the rest keep their result from the audit before.
  4. A second AI agent, which did not write the findings, checks each one again in the code and by experiment, re-checks a sample of the passes, and confirms, changes or drops each finding.
  5. The release gate: no release with an open blocker or high finding, or with any open finding that users may notice, unless the maintainer decides otherwise in writing. Those decisions are marked accepted above.

Next to ASVS it checks our own list, grouped by the ISO/IEC 25010 quality characteristics (stability, reliability, maintainability and the rest), and platform checks for a Mac app: signing, notarisation, the hardened runtime, entitlements, Apple's interface guidelines, accessibility and the privacy manifest. Those checks are ours and are named as ours; ISO's own text is not quoted.

What this does not give: AI agents can miss things a person would find, and nobody outside the project has checked this work. If you find something, the security advisory form reaches me privately.
